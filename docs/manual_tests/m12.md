# M12 manual test — the solid view

**Why this document exists.** Whether the carve is *arithmetically* right is unit-tested against closed
form: a 6 mm cutter leaves a 6 mm slot with walls at exactly ±3 mm, a ball nose leaves the cross-section
of a sphere, a full revolution at constant Z leaves a constant radius. None of that needs a screen.

What a test cannot judge is whether the result **reads as a part**. Shading, whether the surface looks
lit from outside or hollowed from inside, whether a pocket's far wall draws over its near one, whether
the seam of a wrapped cylinder is visible — all of those are properties of a GL context that no test
environment here has. There is also one thing that is a *correctness* question and still only checkable
by eye: whether the solid quietly swallows the selection highlight or the tool marker. See § 4.

Read `m2.md` first if you have not. About fifteen minutes.

## Setup

The shipped profile deliberately declares neither a blank nor a cutter, so start by giving it both.

```bash
.venv/bin/foursight-gui tests/fixtures/baseline_4axis.nc
```

Open **File → Machine profile…** (Ctrl+M), switch **Stock** on as a `box` with
`min = [0, 0, -20]`, `max = [100, 80, 0]`, switch **Tool** on with `diameter = 6`, `shape = flat`, and
Apply.

For § 5 you will want the rotary profile, which ships with both already set:

```bash
.venv/bin/foursight-gui --profile profiles/bamse-rotary.toml tests/fixtures/baseline_4axis.nc
```

---

## 1. The solid appears, and it is shaded

| Step | Expect |
|---|---|
| **View → Solid view** (Ctrl+D) | A grey solid block appears where the blank is; the status bar says "Carving the solid…" then "Solid view: showing the machined result" |
| Orbit around it | Faces facing you are lighter than faces turned away — it reads as a lit object, not a flat silhouette |
| Look at where the program cut | The cut is a visible recess in the top face, not a colour change |
| Look at the block from **below** | A closed underside, not a hollow shell you can see up into |
| Note the floor grid | It **disappears** while the solid is up, and comes back when the solid goes |
| Ctrl+D again | The solid disappears; the toolpath is untouched |

**The property being checked:** that the mesh is closed, its normals point outward, and the machined face
is the **brightest** part of the picture rather than the darkest. The first working build had it the other
way round — pyqtgraph's `shaded` shader lights from eye space, so the face turned toward you renders at
ambient, which is exactly the surface this view exists to show. **If the underside is missing, if the
block looks like a sheet of paper floating in space, or if the top face is darker than the sides**, that
is a real defect.

The grid vanishing is deliberate, not a bug: it is a plane at Z = 0 and stock tops sit at Z = 0, so it
slices through the part and draws over every pocket floor.

## 2. Solid and toolpath are genuinely independent

| Step | Expect |
|---|---|
| With the solid on, **View → Toolpath** (Ctrl+T) | The coloured lines vanish; the solid stays |
| Look at the legend | The Rapid/Feed rows are gone; the **Machined surface** row remains |
| Ctrl+T again | The lines come back, drawn **over** the solid rather than hidden behind it |
| Turn the solid off, leave the toolpath off | An empty viewport with only the grid — not an error |
| Open another file with the toolpath still off | Still off. The menu and the picture agree |

**The property being checked:** two toggles, no implication either way. Lines drawing *over* the solid is
correct and deliberate — the batches never test depth — so it is an x-ray, not a mistake. **If toggling
the toolpath also changes the solid, or a reload silently brings hidden lines back**, that is a defect.

## 3. Ctrl+P still means what it always meant

| Step | Expect |
|---|---|
| With the solid off, press Ctrl+P | The view switches to part coordinates, exactly as it did in M4 |
| Press Ctrl+P again | Back to machine coordinates |
| Now with **box** stock, turn the solid on while part coordinates are on | Part coordinates switches itself **off**, visibly, and the solid appears |
| With the solid on, press Ctrl+P by hand | The solid switches off and the status bar says it needed machine coordinates |

**The property being checked:** that Ctrl+P was not repurposed, and that the *stock shape* decides the
frame rather than the user. A box Z map drawn in part coordinates is not a rougher picture — it is a
picture of somewhere the part is not. **If the checkbox moves without the picture changing**, or the
solid stays on screen across a frame switch, that is a defect.

## 4. The solid does not swallow the overlays

This section is here because it is the one *correctness* claim in M12 that no test in this repository
can make. Both items below draw with depth testing off; the solid is the first thing in this application
ever to write depth.

| Step | Expect |
|---|---|
| With the solid on, click a line in the editor that cuts **inside** the material | The cyan selection highlight is visible **through** the solid, not hidden by it |
| Scroll the editor through several cutting lines | The highlight tracks, and never disappears where the path goes deep |
| Press Ctrl+Space to play | The white tool marker stays visible the whole time, including while the tool is buried in the work |
| Pause mid-cut and orbit | The marker stays on top from every angle |

**The property being checked, and why it is worth four rows:** a selection that vanishes reads as "this
line draws nothing", which is the opposite of what a selection is for, and a tool marker that disappears
reads as the program having finished. Both failures are silent. **If either is occluded by the solid**,
`OVERLAY_GL_OPTIONS` is not reaching the item and that is a real defect.

## 5. Cylindrical stock, in part coordinates

Restart with `--profile profiles/bamse-rotary.toml` and open a program that moves A.

| Step | Expect |
|---|---|
| Ctrl+D | Part coordinates switches itself **on**, and a shaded cylinder appears |
| Orbit to look along the rotary axis | A round bar, capped at both ends |
| Rotate slowly all the way round | **No stripe, crack or ridge** at any one angle |
| Look at where the program cut | A groove that follows the part around, not a straight chord across it |

**The property being checked:** the wrap. The angular axis closes on itself in both the carve and the
mesh, and either one left open produces a defect exactly one tool radius wide, at exactly one angle —
which looks like a feature of the user's program rather than of ours. **A visible seam is a real defect.**

## 6. It says what it cannot show

| Step | Expect |
|---|---|
| Open a program that changes tool (two different T words) and carve | The legend's **Machined surface** row carries a dimmed note naming both tools and saying the others are not modelled |
| Open `tests/fixtures/cutter_comp_span.nc` and carve | A note saying unverified cutting segments were not carved, so more material is shown than the program leaves |
| Carve a program that cuts nothing inside the blank | The status bar says "nothing was removed" rather than showing an untouched block with no explanation |
| Remove `[tool]` from the profile and press Ctrl+D | A dialog explaining that a cutter is needed and is never guessed; the menu item unchecks itself |

**The property being checked:** a shaded solid looks far more authoritative than a line does, so every
limit of the model has to be *on the picture*. A caveat in a document nobody has open is not a caveat.
**If a note is missing, or the menu stays checked after a refusal**, that is a defect.

## What is deliberately absent in M12

Not bugs. Do not file these:

- **Undercuts.** A heightfield stores one number per cell. A T-slot cutter, a dovetail or a boring bar
  reaching under a lip renders as though the material above it were gone too. Lifting this needs a dexel
  or voxel model, which `PLAN.md` § Future still parks post-v1.
- **More than one cutter.** There is no tool table in v1 — T words are numbers nothing resolves to
  geometry. The carve uses `[tool]` throughout and says so when the program disagrees.
- **Untrusted spans do not cut.** A cutter-compensated span is the programmed centreline, not where the
  tool goes. Carving with it would be confidently wrong, so the solid shows extra material instead and
  names the omission.
- **No diagnostics come from the carve.** `geometry.rapid-into-stock` is still a warning and still reads
  the fixed envelope. Nothing in `verify/` reads `[tool]`.
- **Fixtures, clamps and workholding are not modelled at all.**
- **The carve is not cached.** Toggling the solid off and on carves again. It takes well under a second,
  and a held carve is exactly the stale-geometry failure the viewport spends most of its code avoiding.
- **Sharp edges are one cell wide.** Resolution is derived from the stock size and bounded by the tool
  radius; a very large cutter deliberately coarsens the grid rather than stalling the application.
