# M2 manual test — simulation and viewer

**Why this document exists.** PLAN.md keeps the GUI layer thin so that everything worth asserting can
be unit-tested, and most of it is: 872 automated tests cover batching, disclosure, threading and
cancellation. What they cannot check is **pixels and feel** — Qt's `offscreen` platform has no GL
context, so `paintGL` never runs in CI. Everything below is here because a human eye is the only
instrument for it. If a step could be automated, it should be, and it should leave this file.

Run through this before tagging M2. It takes about ten minutes.

## Setup

```bash
.venv/bin/foursight-gui                      # empty window
.venv/bin/foursight-gui tests/fixtures/baseline_4axis.nc   # or open a file directly
```

Baseline hardware for the recorded numbers is the D5 machine in PLAN.md § Rendering Constraints
(Intel Iris Xe, Mesa 25.1.5). On other hardware the *observations* below should still hold; only the
frame rates will differ.

---

## 1. The toolpath is drawn, and drawn correctly

| Step | Expect |
|---|---|
| Open `tests/fixtures/baseline_4axis.nc` | A toolpath appears, framed in view, not a dot in the distance or clipped at the edges |
| Look at the colours | Positioning moves **red**, cutting moves **green**. Both clearly distinguishable |
| Open `tests/fixtures/arc_helical.nc` | Arcs look like **arcs** — smooth curves, not visible polygons or chords cutting corners |
| Open `tests/fixtures/arc_full_circle_ijk.nc` | A **closed circle**, not an arc with a gap or a stray line across the middle |

**The one that matters most:** arcs must not look faceted. Chord tolerance is 0.01 mm, so at any
sane zoom a curve should read as a curve. Visible flat spots mean tessellation has regressed, and
`tests/test_golden.py` should have caught it — if the picture is faceted and the tests pass, the
goldens were re-recorded when they should not have been.

## 2. Orbit, pan, zoom

| Step | Expect |
|---|---|
| Left-drag | The view orbits smoothly. No stutter, no jumping |
| Shift+left-drag | The view pans. **The part stays under the pointer** — it must not lag it, move at half speed vertically, or travel the wrong way |
| Right-drag, then middle-drag | Both pan, and all three pan gestures feel identical |
| Scroll wheel | Zoom in and out, centred sensibly |
| Zoom right in on one corner, then pan | You can reach any part of the program. This is what T11.5 fixed; before it, a trackpad had no pan at all |
| Orbit while zoomed right in | Still smooth; the path does not shimmer or disappear |
| `View → Fit to program` (Ctrl+0) | The whole program is framed again |

Then, with the editor open (M3 onwards), the click/drag boundary — the half of this that is easy to
miss because nothing on screen looks wrong:

| Step | Expect |
|---|---|
| Click a segment | The editor jumps to its line |
| Orbit, and release the button over a segment | **The editor does not move.** A drag is a camera move, never a selection |
| Shift-drag to pan, releasing over a segment | Same: no selection |
| Click a segment as sloppily as you can while still calling it a click | It still selects, and the view does not nudge |

Rotate until you are looking straight down. The grid should be in the **XY plane** with the toolpath
sitting on or above it — if the part appears to lie *inside* the grid plane, the axis mapping is wrong.

## 3. Geometry that is deliberately not drawn

This is the section to take seriously. PLAN.md: *"A previewer that refuses to draw is recoverable; one
that draws the wrong path is worse than no previewer."* A refusal the user never notices forfeits that.

| Step | Expect |
|---|---|
| Open `tests/fixtures/canned_cycle_span.nc` | A **dark red banner** appears above the viewport saying the toolpath is **incomplete**, naming lines 9–12 |
| Look at the viewport | There is **no straight line** running through the drill positions. That span is simply absent |
| Now open `tests/fixtures/baseline_4axis.nc` | The banner **disappears completely** — no leftover text, no empty coloured strip |
| Open `tests/fixtures/cutter_comp_span.nc` | **No banner.** The status bar mentions an unverified span |
| Look at the viewport | The comp span is drawn in **amber**, plainly different from the green feeds around it |

Two failure modes to watch for, both of which look fine at a glance:

- **A banner that stays up** after loading a clean file. That trains the user to ignore it.
- **A banner on the cutter-comp file.** Comp is common in real programs; warning "incomplete" there
  makes the warning worthless, and the geometry *is* complete — it is just not where the tool goes.

## 4. A long file does not freeze the window

Generate a large program first:

```bash
.venv/bin/python -c "
import sys; sys.path.insert(0, 'tests')
from test_perf import generate
open('/tmp/big.nc', 'w').write(generate(100_000))"
```

| Step | Expect |
|---|---|
| Open `/tmp/big.nc` | A progress bar and a **Cancel** button appear in the status bar |
| While it loads, drag the window and orbit the (empty) view | **The window responds.** It must not grey out or show a "not responding" title |
| Watch the status bar | `Parsing…` first, then `Simulating … n of 85,715` with the bar advancing |
| When it finishes | Bar and Cancel button **vanish**. Status shows blocks, segments and an estimated time |
| Orbit the loaded program | Smooth. Recorded: 316 fps median on the baseline machine |

Then test cancelling:

| Step | Expect |
|---|---|
| Open `/tmp/big.nc` again and click **Cancel** partway | Loading stops within a moment |
| Look at the viewport | The **previous** program is still drawn — never a half-drawn toolpath |
| Look at the status bar | It says what is still being shown |
| Open `/tmp/big.nc` again while a load is running | The newer file wins; the title bar ends up naming the file you asked for last |

**A partial toolpath appearing after a cancel is a serious failure**, not a cosmetic one — it would be
a program the machine never runs, drawn as though it were complete.

## 5. Files that cannot be opened

| Step | Expect |
|---|---|
| Load `baseline_4axis.nc`, then `File → Open` a `.png` or any binary file | A dialog says it cannot be opened |
| Dismiss it | The **previous toolpath is still on screen**, still named in the title bar |
| Status bar | Says which file it is still showing |
| `File → Reload` (F5) after editing the open file in another editor | The change appears |

Losing the loaded program to a mistyped filename is the failure this guards.

## 6. Without the GUI extra

```bash
# In an environment without PySide6:
foursight-gui
```

Expect one sentence naming `pip install "foursight-cnc[gui]"`, and a note that `foursight parse` and
`foursight check` still work. **Not** a `ModuleNotFoundError` traceback.

## Recorded numbers (baseline hardware, T2.13)

| Measurement | Value | Requirement |
|---|---|---|
| 100k lines to first frame drawn | 4.46 s | ≤ 5 s |
| Orbit, 81,900 segments | 316 fps (worst frame 4.99 ms) | ≥ 30 fps |
| Orbit, 500k segments | 241 fps (worst frame 10.7 ms) | ≥ 30 fps |
| Geometry + GL at 500k segments | 38.5 + 12.0 MB | ≤ 55 MB |

The time figure has only ~11% margin and is dominated by simulation, not rendering. PLAN.md
§ Performance Requirements sizes the fast path that would recover most of it if slower hardware ever
needs it.

## What is deliberately absent in M2

Not bugs — later milestones. Do not file these:

- No editor pane, no click-a-line-to-highlight, no click-a-segment-to-jump (M3, and picking is
  undecided: D4).
- No timeline or playback (M3/M4).
- No rotary kinematics: a table-mount program is drawn in **machine** coordinates, so a wrapped path
  looks like the tool path rather than the shape on the part (M4).
- No fixes offered for diagnostics; `foursight check` reports, nothing repairs (M5).
- Tool length offsets (G43/G44) are not modelled — the status bar says so when a program uses them.
