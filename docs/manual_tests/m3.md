# M3 manual test — editor sync and diagnostics

**Why this document exists.** M3's whole value is that four views agree about one program: the code pane,
the toolpath, the diagnostics list and the timeline. Whether they *agree* is heavily unit-tested — 1049
tests, and the ones that matter assert the partition, the orderings and the tier distinctions. What only a
human can judge is whether the agreement is **legible**: whether the highlight is findable, whether
`unsupported` reads differently from a warning at a glance, whether scrubbing feels like following a tool.

Read `m2.md` first if you have not; this only covers what M3 added. About fifteen minutes.

## Setup

```bash
.venv/bin/foursight-gui tests/fixtures/baseline_4axis.nc
```

The window is code on the left; toolpath, timeline and diagnostics on the right.

---

## 1. Syntax highlighting agrees with the parser

| Step | Expect |
|---|---|
| Look at any motion line | G-codes and M-codes bold and distinctly coloured; axis words, arc words (IJKR), feeds and tool words each their own colour |
| Find a comment | Comment-coloured for its whole extent, including the brackets |
| Open `tests/fixtures/framing_fanuc.nc` | The leading `%` is **not** marked as an error |
| Open `tests/fixtures/block_delete.nc` | The leading `/` is distinctly coloured — it decides whether the line runs |
| Type `G1 X Y10` on a blank line | `X` gets a **red wavy underline** |
| Type `G1 X10 (note) Y20` | The comment stays comment-coloured; the words either side keep theirs |

**The property being checked:** anything the editor paints as a valid word must be a word
`foursight check` accepts, and vice versa. If you find a construct the editor flags that the CLI accepts —
or the reverse — that is a real defect, not a cosmetic one. Cross-check with:

```bash
.venv/bin/foursight parse <the file>
```

## 2. Cursor → toolpath

| Step | Expect |
|---|---|
| Click a motion line in the code pane | Its segments light up **cyan** in the viewport; the status bar says how many |
| Hold ↓ and walk down the program | The highlight follows, smoothly, with no lag |
| Land on an arc line | The **whole arc** lights up, not one facet of it |
| Land on a comment or an `M` line | The highlight clears; status says **"no motion"** |
| Open `canned_cycle_span.nc`, click a line inside the cycle | Status says **"not drawn"** and names the reason — *not* "no motion" |
| Orbit so the selected line is behind other geometry | The highlight is **still visible** through it |

Two things worth dwelling on. The **"not drawn" versus "no motion"** distinction is the point of the
readout: a drill cycle that says "no motion" would tell you your program does nothing. And the highlight
being visible through geometry is deliberate — if it hid behind the part you would read that as the line
drawing nothing.

## 3. Toolpath → cursor

| Step | Expect |
|---|---|
| Click directly on a line in the viewport | The cursor jumps to that source line and the whole line highlights |
| Click the **far end** of a long rapid | You get *that rapid*, not a short move that happens to be nearby |
| Click empty space | Nothing changes — the previous selection stays |
| **Orbit, then click a segment** | The correct line. This is the one to try hard to break |
| Zoom right in, click a segment | Still correct |
| Resize the window, click a segment | Still correct |

**Orbit-then-click is the important case.** The screen projection is cached, and a cache left over from
before the orbit would return a *confidently wrong* line with nothing on screen to suggest it. The cache
is keyed on the camera matrix so this should be impossible — but it is the failure worth trying to
provoke, because it is invisible when it happens.

## 4. Diagnostics panel

| Step | Expect |
|---|---|
| Open `baseline_4axis.nc` | Panel says **"No problems found"** |
| Open `canned_cycle_span.nc` | One **`unsupported`** row, with its own colour *and* symbol |
| Compare against a warning | Different colour **and** different symbol — squint, or take a screenshot and desaturate it |
| Click a row | The editor jumps to that line and it highlights |
| Walk the list with ↓ | Each row jumps as it is selected — no double-click needed |
| Open a large generated file (see §5) | The header says e.g. *"14286 error · 141672 warning (showing the first 2,000 of 155,958)"* |

**`unsupported` must not read as a warning.** They are not degrees of the same thing: a warning says
"look at this", `unsupported` says "part of the picture is missing". If the two are hard to tell apart at
a glance, that is a real problem — this panel is the only place the tiers appear side by side.

**Truncation must be visible.** "Showing everything" and "showing the first 2,000" look identical unless
the header says which.

## 5. A long file: geometry first, diagnostics after

```bash
.venv/bin/python -c "
import sys; sys.path.insert(0, 'tests')
from test_perf import generate
open('/tmp/big.nc', 'w').write(generate(100_000))"
.venv/bin/foursight-gui /tmp/big.nc
```

| Step | Expect |
|---|---|
| Watch the load | Progress bar, then the toolpath appears at roughly **6 s** |
| Look at the panel at that moment | It says **"Checking…"** — not "No problems found" |
| Wait | Diagnostics fill in a few seconds later (about 12.5 s total) |
| While it is checking, orbit and click | The window stays responsive throughout |

**"Checking…" rather than an empty list** matters: an empty panel reads as a clean bill of health, which
is a claim not yet earned at that point.

## 6. Timeline scrubber

| Step | Expect |
|---|---|
| Open `baseline_4axis.nc` and drag the slider | The editor follows the tool through the program; readout shows `position / total` and the line |
| Drag to the far right | The readout reaches the total, not 90% of it |
| Open a program with no feed rates (`G1 X10` with no `F`) | The slider is **disabled**, because there is no time to scrub through |
| Open a file where only *some* moves lack a feed | The readout says **"total is short"** and how many segments lack a rate |
| Compare the total against the status bar's estimate | They agree |

A partial total presented as the cycle time would be inventing a number, and it would look entirely
plausible — hence the caveat.

## What is deliberately absent in M3

Not bugs; later milestones. Do not file these:

- **No rotary kinematics.** A table-mount program is still drawn in **machine** coordinates, so a wrapped
  4-axis path looks like the tool's path, not the shape on the part (M4). This is the biggest remaining
  gap and the one most likely to look wrong to a machinist.
- **No fixes.** Diagnostics report; nothing repairs them (M5).
- **No playback**, only scrubbing — the timeline has no play button. *(Answered in M10: it needed one.
  See `m10.md`.)*
- **Tool length offsets (G43/G44) are not modelled**; the status bar says so when a program uses them.
- **No verifier rule for the unmodelled tool length** — it is a simulator note, not a diagnostic, so it
  appears in the status bar rather than the panel. Owed work, recorded in PLAN.md.
