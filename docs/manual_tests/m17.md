# M17 manual test — importing a Mach3 profile

**Why this document exists.** The mapping is unit-tested against five fixtures, including the refusals,
and the form is tested through `propose`. What no test can judge is whether the review table **tells the
truth legibly** — whether an operator looking at a row can see where the number came from and decide
whether to take it. That judgement is the whole point of the dialog: an import nobody reads is a config
file written by a machine that has never seen the machine.

It is also where two real defects were found by looking rather than by asserting. `QTextBrowser` read
`<Rot360>` as an unknown HTML element and rendered the note with its subject silently missing, and a
`*display*` written for Markdown showed its asterisks. Both were invisible offscreen, because the plan
object was correct in each case. Assume anything that renders a tag name is still capable of eating it.

About fifteen minutes. You need a Mach3 profile `.xml`; the two under
`~/Desktop/CNC/Mach3 profiles/` are the ones the milestone was built against, and
`tests/fixtures/mach3/` holds trimmed versions of the same machine.

## Setup

```bash
.venv/bin/foursight-gui tests/fixtures/baseline_4axis.nc
```

Open the machine-profile editor, then **Import from Mach3…**.

---

## 1. The table says where every number came from

| Step | Expect |
|---|---|
| Choose `Rotary.xml` | A table of 19 rows, and a *Not imported, and why* list under it |
| Read the **From Mach3** column | Every row names the tag and its raw value — `<Vel0>85. per second`, `<IJMode>1` |
| Read `[axes.x].max_rapid` | `5100.0 mm/min`: the file's 85 units/second, times 60 |
| Read `[axes.a].max_rapid` | `3000.0 deg/min` — **degrees**, and it must stay degrees in step 3 |

**The question to ask yourself:** if one of these numbers were wrong by 60x or 25.4x, would this table
show you? If a row's source column does not let you check the arithmetic in your head, that is a finding.

## 2. The rows that are not ticked

| Step | Expect |
|---|---|
| Look at `[axes.x].min` / `.max` | **Unticked**, with a note saying Mach3 is not enforcing soft limits |
| Hover the note | The full sentence, not an ellipsis |
| Look at `[limits].max_feed` | **Unticked** — Mach3 has no such setting; this is a derivation |
| Look at `[limits].max_spindle_rpm` | Ticked, `25000.0 rpm`, from the highest pulley rather than the selected one |

`Rotary.xml` says X spans 745…970 and `Mach3Mill.xml`, for the same motors, says −2…600. Soft limits
that nothing enforces are numbers that have never had to be true. Ticking them by default would make
`geometry.axis-travel-exceeded` confidently wrong about a correct program.

## 3. The units selector

| Step | Expect |
|---|---|
| Switch **Mach3 native units** to `inch` | An amber banner: a 129540 mm/min rapid is not a machine |
| Look at the linear rows | Every length and rate is now 25.4x larger |
| Look at `[axes.a].max_rapid` | **Unchanged at 3000.0 deg/min** — 25.4 x an angle is not an angle |
| Switch back to `mm` | The banner goes, the numbers return |

The banner catches the destructive direction reliably (a metric machine read as inch is unmistakable).
The other direction shrinks into plausible numbers, which is why the selector exists at all: you are the
check. If your own machine's rapid rate does not look like your machine, do not press Import.

## 4. The conflict that writes nothing

Needs a profile where Mach3 short-rotates and the FourSight profile's A axis does not wrap —
`tests/fixtures/mach3/shortrot.xml` against a profile edited to `wrap = false`.

| Step | Expect |
|---|---|
| Find `[axes.a].short_rotate` | Greyed, unticked, **not** tickable, value `conflict — nothing written` |
| Read its note | It names `<ShortRot>1`, says `wrap` is false, and asks whether the table turns continuously |
| Press **Import**, then **Apply** | The profile applies, and `short_rotate` is unchanged |

The loader is right to refuse `short_rotate` without `wrap`. Mach3 has the two as independent
checkboxes, so this pair is expressible in the controller and not in a profile — and an importer that
quietly wrote `wrap = true` to make it fit would manufacture the very agreement you opened the dialog to
check.

## 5. Into the form, not into the profile

| Step | Expect |
|---|---|
| Press **Import** | The dialog closes; the form shows the new values; **Apply** and **Revert** light up |
| Look at the window title bar behind it | The loaded profile has **not** changed yet |
| Press **Revert** | Every imported value goes back. Nothing was applied |
| Import again, press **Apply** | The profile changes, and the program re-verifies against it |
| Check `Units of this file` | Still `mm`. An import never writes it |

`[machine].units` is the one key an import must never touch: changing it reinterprets every key the
import did *not* touch by 25.4x, with no diff to look at, because none of those lines change.

## 6. What it refuses to guess

| Step | Expect |
|---|---|
| Read the *Not imported* list | `[kinematics]` (all four keys), `[stock]`, `[tool]`, `[offsets]`, `[safety]`, `[tolerance]` |
| Find `[kinematics].rotary_axis` | It explains that `<AParallel>` and `<AtoX/AtoY/AtoZ>` are display settings |
| Find `[stock].diameter` | It explains that `<RadiusA>63.` is a feedrate radius, not the blank |
| Import `Mach3Mill.xml` instead | `[axes.a]` is absent from the table and present in the notes, because `<Motor3Active>0` |

A guessed `rotary_axis` draws a confidently wrong toolpath, which is the one thing this tool exists not
to do. If any row in the table ever looks like it was inferred rather than read, that is a finding.
