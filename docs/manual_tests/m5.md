# M5 manual test — fixes and packaging

**Why this document exists.** The fix engine is heavily unit-tested, including every refusal, and the
one-fix contract is asserted on rebuilt line numbers rather than on text. What tests cannot judge is
whether a diff is **reviewable** — whether a machinist looking at it for four seconds can tell what will
change and decide. That is the whole safety mechanism of this milestone, and it is a human judgement.

There is also one thing here that no test in this repository can cover: **the bundle**. The suite imports
normally, so it cannot see what PyInstaller leaves out. Both packaging bugs in M5 were found by running the
bundle, not by testing.

Read `m2.md` and `m3.md` first. About twenty minutes, plus a build.

## Setup

```bash
.venv/bin/foursight-gui tests/fixtures/baseline_4axis.nc
```

---

## 1. A diff is reviewable

| Step | Expect |
|---|---|
| Open any program without `M30`; `Fix → Append M30` | A dialog shows a unified diff with one `+` line |
| Read it | The change is obvious in a few seconds without scrolling |
| Press **Cancel** | Nothing changes. The buffer, the toolpath and the diagnostics are all untouched |
| Repeat and press **Apply** | The line appears in the editor, and the diagnostics re-run |

**The question to ask yourself:** if this diff had been subtly wrong, would you have noticed? If the answer
is no because the diff was hard to read, that is a real finding — the preview is the only thing standing
between a fix and the machine.

| Step | Expect |
|---|---|
| `Fix → Add safety preamble` on a program that already has `G21` | The diff adds `G90` and `G17` but **not** `G21` |

A diff that rewrites lines it did not need to makes the real change harder to see. If you find a fix
touching lines it had no reason to, file it.

## 2. Refusals

These are the point of the milestone. A fix that acts when it should decline produces a program that looks
corrected and machines something else.

| Step | Expect |
|---|---|
| Write `G21 G90 G17` / `G0 X0 Y0` / `G2 X20 Y0 I12 J0 F600`, put the cursor on the arc, `Fix → Recompute arc centre` | A **refusal** dialog: no Apply button, a reason naming the mismatch in mm, and advice to check the arc by hand |
| Change `I12` to `I10.02` and repeat | Now it **applies**, and the note says both endpoints were preserved |
| `Fix → Convert IJK arc to R` on a full circle (`G0 X10 Y0` then `G2 X10 Y0 I-10 J0`) | A **refusal** explaining that R cannot express a full circle |

Two things to check about the refusals:

- **No Apply button at all**, not a greyed-out one. A disabled button invites the user to try again harder.
- **The reason is actionable.** "Cannot fix" alone is barely better than a wrong fix; it should say how far
  out the geometry is and what to do next.

## 3. The one-fix contract

| Step | Expect |
|---|---|
| Open a program with **no** preamble, note the line number of the first cutting move | — |
| `Fix → Add safety preamble`, Apply | Two lines are inserted at the top |
| Click that first cutting move in the **viewport** | The editor jumps to its **new** line number, not the old one |
| Click a diagnostic in the panel | It also lands on the correct line |
| Scrub the timeline | Positions match the new numbering |

This is the contract working. A fix shifts every line number after it, so everything — diagnostics,
segments, picking, the timeline — is rebuilt from scratch. If any of them lands one or two lines off, the
re-parse is not happening.

| Step | Expect |
|---|---|
| `Fix → Undo last fix` | The buffer returns to exactly its previous state, and everything re-runs again |

## 4. The file on disk is never written

| Step | Expect |
|---|---|
| Note the file's modification time (`ls -l part.nc`) | — |
| Apply two or three fixes | The editor changes each time |
| Check the modification time again | **Unchanged.** Nothing has been written |

Fixes modify the editor buffer; saving is explicit. If the file changed on disk without you saving, stop and
file it — that is data loss, not a bug.

## 5. Destructive fixes

| Step | Expect |
|---|---|
| Look at the `Fix` menu | `Strip N-word line numbers` is labelled **(destructive)** and has no keyboard shortcut |
| Run it on a program with N-numbers | A **dark banner** above the diff, not a footnote, plus a note about jump targets and mid-program restarts |

The diff shows which lines changed. It cannot show that a `GOTO N120` no longer has a target — which is
exactly why the warning has to be more prominent than the diff itself.

## 6. Large and awkward files

| Step | Expect |
|---|---|
| Open a `.png` or any binary file | Refused as binary, previous program still on screen |
| Open a file saved by Notepad on Windows (CRLF) | Loads normally; line numbers in the gutter match the file |
| Apply a fix to that CRLF file, then save | **The file is still CRLF.** Not silently converted to LF |
| Try to open something enormous (a video, say) | Refused with a size message, not an out-of-memory kill |

The CRLF one deserves attention: the editor normalizes line endings internally, so a fix could silently
rewrite the whole file's terminators. That change would not appear in the diff at all, because a unified
diff shows no line endings.

## 7. The bundle — nothing here is covered by tests

```bash
.venv/bin/python scripts/build.py
DISPLAY=:0 ./dist/foursight/foursight tests/fixtures/baseline_4axis.nc
```

| Step | Expect |
|---|---|
| Launch the bundle | The window opens and draws the toolpath |
| Look at the diagnostics panel | Findings appear — **not** an empty list |
| Open `canned_cycle_span.nc` in the bundle | The `unsupported` diagnostic appears |
| `Fix` menu | All eight fixes are listed |

**Why the diagnostics panel is the thing to check.** Two registries are populated by *dynamic* import, so
that `ruff --fix` cannot delete the import and leave them silently empty. PyInstaller cannot see through a
dynamic import either, so without `--collect-submodules` the modules are simply absent from the bundle —
and a program with no diagnostics looks exactly like a clean program. Both packaging bugs in M5 were found
this way and neither was visible to any test.

Also build and check the CLI, which exercises the rule registry directly:

```bash
.venv/bin/python scripts/build.py --entry src/foursight/cli.py --name foursight-cli
./dist/foursight-cli/foursight-cli check tests/fixtures/canned_cycle_span.nc
```

Expect **one `unsupported` diagnostic**. "No problems found" here means the rule registry is empty and the
bundle is broken in a way that looks like good news.

## 8. Windows

Not yet done, and it is the one gap in the milestone: the Windows bundle is built in CI but has never been
launched on a clean Windows VM (T0.8/T0.9). When one is available:

| Step | Expect |
|---|---|
| Copy the bundle to a machine with **no** Python and no Visual C++ redistributable installed | — |
| Run `foursight.exe part.nc` | The window opens and draws |
| Check the diagnostics panel | Populated, per §7 |

Run the build **without** `--windowed` for this, so the console keeps the output that says how it failed.

## What is deliberately absent

- **No tool table**, so G43/G44 is reported `unsupported` and drawn with a shifted Z datum.
- **No stock model**, so rotary step sizing uses path radius as a proxy for part radius.
- **No cutter-compensation geometry**; the programmed centreline is drawn and marked unverified.
- **No batch fix application.** One fix at a time is the contract, not a limitation to be lifted.
