# M11 manual test — the colour legend

**Why this document exists.** Whether the legend lists the right rows is unit-tested, and so is the fact
that it reads its colours off the batches rather than restating them. What a test cannot judge is whether
it **works as a key**: whether you can read it against a dense toolpath, whether the swatch colour is
convincingly the same colour as the lines it names, and whether it sits somewhere that helps rather than
covering the part you were looking at.

There is also one thing offscreen tests cannot see at all — see § 1.

Read `m2.md` first if you have not. About ten minutes.

## Setup

```bash
.venv/bin/foursight-gui tests/fixtures/cutter_comp_span.nc
```

This fixture is the one that exercises every row: it has rapids, feeds and an unverified span.

---

## 1. The legend is actually drawn over the GL view

| Step | Expect |
|---|---|
| Look at the top-left of the toolpath pane | A dark translucent panel listing colours and names, **on top of** the 3D view |
| Orbit and zoom | It stays pinned to the top-left corner and does not move with the geometry |
| Drag the splitter to make the viewport very narrow, then very wide | It stays in the corner; it never overlaps the timeline bar or escapes the pane |
| Look at the toolpath *behind* the panel | Geometry is dimmed but still visible through it |

**The property being checked, and the reason this section is first:** the offscreen tests can prove the
overlay is parented and positioned correctly, but they cannot prove a child widget actually **composites
over an OpenGL surface** — there is no GL context in the test environment. Qt 6 renders `QOpenGLWidget`
into a framebuffer and composites the widget tree over it, so this is expected to work, but it has to be
seen on a real driver. **If the panel is invisible, or appears as a black rectangle with no toolpath
behind it, that is a real defect** and the fallback is to move the legend to a strip under the viewport.

## 2. The key names what is on screen, and only that

| Step | Expect |
|---|---|
| With `cutter_comp_span.nc` open | Rows for **Rapid**, **Feed** and **Feed (unverified)** |
| Hover the panel | A tooltip: unverified spans are the programmed centreline, which is not where the tool goes |
| Open `tests/fixtures/baseline_4axis.nc` | The **unverified row disappears** — that program has none |
| Open `tests/fixtures/canned_cycle_span.nc` | Rows match what is actually drawn; the suppressed span contributes nothing |
| Click a motion line in the code pane | A **Selected line** row appears in cyan |
| Click in the trailing blank line past the end of the program | The Selected line row goes away again |
| Press play | A **Tool position** row appears, with a **dot** swatch rather than a line |
| Let playback finish, then open another file | No Tool position row until you play again |

**The property being checked:** the legend describes the current picture, never the palette in the
abstract. A row for a colour that is not on screen would teach you to skim past the key — and the
unverified row *appearing* is itself the warning. If you ever see a row for something you cannot find in
the viewport, or a colour in the viewport with no row, that is a real defect.

## 3. The swatches match the lines

| Step | Expect |
|---|---|
| Compare the Rapid swatch against a positioning move | The same red |
| Compare the Feed swatch against a cutting move | The same green |
| Compare the unverified swatch against the comp span | The same amber |
| Look at the two unverified rows if a program has both | Untrusted rapids are **orange**, untrusted feeds are **yellow** — two different ambers, not one |
| Select a line and compare the Selected swatch | The same cyan as the highlight |

**The property being checked:** the swatch is drawn from the very colour value uploaded to GL, so these
should match exactly rather than approximately. A swatch that is merely *close* means someone has
introduced a second copy of the palette.

**Look hard at places where the path crosses itself**, especially on a wrapped rotary program. Every
pixel of toolpath must be one of the colours in the key. This is where the first run of the legend found
a real bug: overlapping lines used to have their colours *added* together, so a red rapid crossing a
green feed appeared yellow — a colour in no palette and, correctly, in no legend. If you see any colour
on the toolpath that the key does not list, that is the same class of defect and worth filing.

## 4. The toggle

| Step | Expect |
|---|---|
| Open the View menu | **Legend** is checked, with `Ctrl+L` |
| Press `Ctrl+L` | The panel disappears; the toolpath is unchanged |
| Press `Ctrl+L` again | It comes back with the same rows |
| Turn it off, then apply a fix (Fix ▸ Append M30 on a program lacking one) | It **stays off** across the reload |
| Turn it off and open a different file | Still off |
| Start the app with no file | No panel — there is nothing to name yet |

**The property being checked:** off means off. Every applied fix reloads the program from scratch, and a
key that switched itself back on each time would be a preference you cannot actually set.

## What is deliberately absent in M11

Not bugs. Do not file these:

- **Rows are not clickable.** Clicking Rapid to hide all rapids is the obvious next request and a real
  feature — the viewport has no per-batch visibility today.
- **No legend for the code pane's syntax colours, or for the diagnostics tiers.** Both already carry a
  second channel: malformed words get a wavy underline, and each severity has its own symbol as well as
  its own colour. The viewport is the one pane that cannot do that to its geometry, which is the whole
  reason this legend exists.
- **The grid and the background are not named.** They are not information about the program.
- **No colour customisation.** The palette is fixed in `batching.py` and `legend.py`.
